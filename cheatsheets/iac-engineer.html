Terraform Module Generator

As Needed

Generate a production-ready Terraform module with variables, outputs, validation rules, and usage examples for a specific resource.

Generate a production-ready Terraform module for [resource type, e.g., AWS RDS PostgreSQL instance / Azure AKS cluster / GCP Cloud Run service]. Requirements: - Cloud provider: [AWS / Azure / GCP] - Terraform version: [>= 1.5 / >= 1.8 / etc.] - Provider version constraint: [e.g., ~> 5.0 for AWS] - Environment pattern: [dev/staging/prod or workspace-based] - Naming convention: [e.g., {project}-{env}-{resource}] - Compliance requirements: [encryption at rest, VPC-only, tagging policy, etc.] The module should include: 1. main.tf - resource definitions with sensible defaults 2. variables.tf - all inputs with descriptions, types, defaults, and validation blocks 3. outputs.tf - useful outputs (ARN, endpoint, ID, connection string) 4. versions.tf - required_providers and terraform version constraints 5. locals.tf - computed values and tag merging 6. README.md usage example showing how to call the module 7. A tfvars.example file for each environment Follow these best practices: - Use variable validation blocks for input constraints - Add lifecycle rules where appropriate (prevent_destroy, ignore_changes) - Include default tags that merge with user-provided tags - Use data sources instead of hardcoded IDs where possible - Add comments explaining non-obvious decisions
Pro Tip: Always run `terraform fmt` and `terraform validate` on generated code before committing. Ask Claude to also generate a `.pre-commit-config.yaml` for automated checks.

Terraform State Troubleshooter

As Needed

Diagnose and resolve Terraform state issues: state drift, import planning, state surgery, and lock conflicts.

I'm having a Terraform state issue and need help diagnosing and resolving it. Problem: [Describe the issue: e.g., "terraform plan shows resources to destroy that shouldn't be destroyed" / "state lock won't release" / "resource exists in AWS but not in state" / "need to move resources between state files"] Current setup: - Backend: [S3 + DynamoDB / Azure Blob / GCS / Terraform Cloud] - State file location: [bucket/path or workspace name] - Terraform version: [version] - Number of resources in state: [approximate count] - Error message (if any): [paste exact error] What I've tried: [any steps already attempted] Help me: 1. Diagnose the root cause of this state issue 2. List the exact terraform CLI commands to resolve it (state mv, state rm, import, force-unlock, etc.) 3. Explain what each command does and its risk level 4. Provide a rollback plan if the fix goes wrong (state backup strategy) 5. Suggest preventive measures to avoid this issue recurring 6. If this involves state surgery, provide a step-by-step runbook with verification at each step IMPORTANT: Flag any destructive operations clearly. I want to understand the blast radius before running anything.
Pro Tip: Always run `terraform state pull > backup-$(date +%Y%m%d-%H%M%S).tfstate` before any state surgery. A backup costs nothing; a corrupted state costs hours.

Requirements: - Template format: [YAML / JSON] - Environment support: [dev/staging/prod via parameters and conditions] - Region: [us-east-1 / multi-region / etc.] - Networking: [existing VPC ID to reference / create new VPC / etc.] - Security requirements: [encryption at rest, TLS, least-privilege IAM, VPC endpoints] - Tagging policy: [required tags: Environment, Owner, CostCenter, Project] The template should include: 1. Help me design an AWS Landing Zone for our organisation. Context: - Organisation size: [number of teams / business units] - Current AWS footprint: [greenfield / existing accounts to migrate] - Compliance requirements: [SOC2 / HIPAA / PCI-DSS / FedRAMP / none specific] - Workload types: [web apps, data analytics, ML, SaaS platform, etc.] - Networking needs: [hybrid with on-prem / cloud-only / multi-region] - Tooling preference: [AWS Control Tower / custom with CloudFormation / Terraform] Design a landing zone blueprint covering: 1. Pro Tip: Start with AWS Control Tower if you can. It gives you guardrails, account factory, and SSO out of the box. Customise on top rather than building from scratch.

Ansible Playbook Generator

As Needed

Create an Ansible playbook with roles, handlers, templates, and idempotent tasks for a server configuration scenario.

Generate a production-ready Ansible playbook for [scenario: e.g., "configuring Nginx as a reverse proxy with TLS" / "hardening Ubuntu 22.04 servers per CIS benchmarks" / "deploying a Java application with Tomcat"]. Environment: - Target OS: [Ubuntu 22.04 / RHEL 9 / Amazon Linux 2023 / etc.] - Ansible version: [>= 2.14 / >= 2.16] - Inventory pattern: [static INI / dynamic AWS EC2 / etc.] - Connection method: [SSH key / SSM / etc.] - Secrets management: [Ansible Vault / external lookup from AWS SSM / HashiCorp Vault] Generate the following file structure: 1. site.yml - main playbook with role includes 2. roles/[role_name]/tasks/main.yml - idempotent tasks with proper check mode support 3. roles/[role_name]/handlers/main.yml - service restart/reload handlers 4. roles/[role_name]/templates/ - Jinja2 templates with sensible defaults 5. roles/[role_name]/defaults/main.yml - default variables 6. roles/[role_name]/vars/main.yml - platform-specific variables 7. roles/[role_name]/molecule/default/ - test scenario for molecule Best practices to follow: - Every task must be idempotent (no shell/command without creates/removes) - Use handlers for service restarts, not inline restarts - Tag every task for selective execution - Use `ansible.builtin.` FQCN for all modules - Include a `--check` compatible mode (no changes in dry run)
Pro Tip: Run `ansible-lint` on generated playbooks before committing. It catches non-idempotent patterns, missing FQCN, and deprecated modules.

Secret Management Strategy

Per Project

Design a secrets management approach using Vault/SOPS/AWS Secrets Manager with rotation policies and access patterns.

Help me design a secrets management strategy for our infrastructure-as-code workflows. Current state: - How secrets are stored today: [hardcoded in code / .env files / encrypted in git / parameter store / etc.] - IAC tools: [Terraform / CloudFormation / Ansible] - CI/CD platform: [GitHub Actions / GitLab CI / Jenkins] - Cloud provider: [AWS / Azure / GCP] - Compliance requirements: [rotation frequency, audit logging, encryption standard] - Types of secrets: [DB passwords, API keys, TLS certs, SSH keys, service account tokens] Design a secrets management system covering: 1. Tool selection: recommend the right tool for our stack - Evaluate: HashiCorp Vault vs SOPS vs AWS Secrets Manager vs Azure Key Vault - Justify the recommendation with pros/cons for our use case 2. Architecture: - Where secrets are stored (source of truth) - How IAC references secrets (data sources, env vars, dynamic providers) - How CI/CD pipelines access secrets without storing them 3. Rotation strategy: - Automated rotation for each secret type - Zero-downtime rotation pattern (dual-credential approach) - Rotation schedule and alerting for expiring secrets 4. Access control: - Least-privilege policies per team/service - Audit logging and alerting on unusual access - Break-glass procedure for emergencies 5. Migration plan: - Step-by-step to move from current state to target state - How to handle secrets already in Terraform state files Provide actual configuration snippets (Vault policies, IAM policies, Terraform code) not just architecture diagrams.
Pro Tip: Scan your repos with `trufflehog` or `gitleaks` before designing the new system. You need to know what's already leaked before you can secure the future.

Change Management Runbook

As Needed

Create a step-by-step runbook for a high-risk infrastructure change with pre-checks, execution steps, verification, and rollback procedures.

Create a detailed change management runbook for: [describe the change: e.g., "migrating RDS from MySQL 5.7 to 8.0" / "replacing NAT Gateways with NAT instances" / "upgrading EKS cluster from 1.28 to 1.29" / "migrating Terraform state backend from S3 to Terraform Cloud"] Change context: - Environment: [production / staging / all] - Maintenance window: [date, time, duration available] - Expected downtime: [zero / X minutes / degraded performance] - Stakeholders to notify: [teams, customers, on-call] - Rollback feasibility: [easy / partial / impossible -- explain constraints] Generate a runbook with: 1. Change Summary: - What's changing and why (1 paragraph) - Blast radius: what services/users are affected - Risk level: low / medium / high / critical 2. Pre-Change Checklist: - Backups verified (specific commands to verify) - Monitoring baseline captured - Communication sent to stakeholders - Rollback plan reviewed by second engineer - Go/no-go criteria 3. Execution Steps: - Numbered steps with exact commands - Expected output after each step - Checkpoint: verify before proceeding to next step - Estimated time per step 4. Verification: - Health checks to run immediately after - Functional tests to validate the change - Monitoring dashboards to watch for 30 minutes post-change 5. Rollback Procedure: - Trigger criteria: when to roll back - Step-by-step rollback commands - Verification that rollback was successful 6. Post-Change: - Documentation updates needed - Monitoring adjustments - Stakeholder communication (success or rollback) - Lessons learned template Format as a checklist I can print and follow step-by-step during the maintenance window.
Pro Tip: Do a dry run of the entire runbook in staging first. Time each step. The maintenance window estimate should come from the dry run, not from guessing.
