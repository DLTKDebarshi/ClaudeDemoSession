🔑 IAM & Access Control

IAM Policy Generator (Least Privilege)

As Needed
When you need to create a tightly scoped IAM policy for a workload instead of using overly broad managed policies.
Generate a least-privilege IAM policy for [AWS / GCP / Azure] that grants only the permissions needed by [service/workload name]. What the workload does: - [e.g. "Reads from S3 bucket X, writes to DynamoDB table Y, publishes to SNS topic Z"] - [e.g. "Pulls container images from ECR, writes logs to CloudWatch"] - [e.g. "Invokes Lambda function A, reads secrets from Secrets Manager path /app/prod/*"] Environment: [account ID / project ID, region, VPC] Identity type: [IAM role for EC2/Lambda/ECS task / service account / user] The policy must: 1. Use specific resource ARNs (no wildcards on resources unless absolutely necessary) 2. Include conditions: [aws:SourceVpc, aws:PrincipalTag, StringEquals on specific keys, IP restrictions] 3. Add explicit Deny statements for sensitive actions (iam:*, sts:AssumeRole to admin roles, s3:DeleteBucket, etc.) 4. Separate read-only vs. write permissions into distinct policy statements 5. Include comments/descriptions explaining why each permission is needed Also provide: - A trust policy / assume role configuration - Recommended SCPs or permission boundaries to layer on top - A checklist of permissions to review and remove after 30 days if unused (using Access Analyzer data)
Pro Tip: After deploying, use IAM Access Analyzer or GCP Policy Analyzer to verify no unused permissions remain after 30 days, then ask Claude to generate the trimmed policy.

IAM Audit & Overprivileged User Detection

Monthly
When conducting a periodic IAM review to identify over-permissioned identities and stale credentials.
Analyse the following IAM configuration data and identify security risks: IAM credential report / policy data: ``` [paste IAM credential report CSV, or policy JSON, or gcloud/az CLI output] ``` Cloud provider: [AWS / GCP / Azure] Organisation structure: [single account / multi-account with AWS Orgs / GCP folders] Please identify and categorise: 1. **Overprivileged Roles/Users** - Roles with AdministratorAccess or Owner that should be scoped down - Wildcard permissions (Resource: "*") that can be narrowed - Unused permissions (last accessed > 90 days) 2. **Stale Credentials** - Access keys older than [90 / 180 / 365] days - Users with console access but no recent login - Service accounts with keys that should use workload identity instead 3. **Policy Anti-Patterns** - Inline policies that should be managed policies - NotAction/NotResource misuse that creates unintended access - Missing MFA conditions on sensitive operations 4. **Cross-Account / Federation Risks** - Overly permissive trust policies (Principal: "*") - External account access without conditions Output a prioritised remediation table: finding, severity (Critical/High/Medium/Low), affected identity, recommended fix, and estimated effort.

Service Account & Workload Identity Design

Per Project
When designing the identity architecture for a new project or migrating from long-lived credentials to workload identity federation.
Design a service account and workload identity architecture for [project/application name] on [AWS / GCP / Azure]. Application architecture: - Services: [list microservices and their runtime: EKS pods, Lambda functions, EC2 instances, Cloud Run, etc.] - Cross-account needs: [does any service access resources in another account/project?] - External integrations: [GitHub Actions, Terraform Cloud, third-party SaaS needing API access] - Data stores: [S3/GCS, RDS/CloudSQL, DynamoDB, Secrets Manager, etc.] Design: 1. **Service account per service** - naming convention, one service account per microservice, principle of least privilege 2. **Workload identity federation** - eliminate long-lived keys: - Kubernetes: [IRSA for EKS / Workload Identity for GKE / Azure AD Pod Identity] - CI/CD: OIDC federation for [GitHub Actions / GitLab CI] with subject claim conditions - External: STS AssumeRoleWithWebIdentity patterns 3. **Cross-account access** - role chaining, trust policies with external ID, session tags 4. **Role bindings matrix** - table mapping each service to its service account, roles, and accessible resources 5. **Key rotation policy** - for any remaining long-lived credentials, define rotation schedule and automation 6. **Break-glass procedure** - emergency access pattern with audit trail Include Terraform/IaC code snippets for the key configurations.
🛡 Threat Modelling & Architecture

STRIDE Threat Model

Per Feature
When a new feature or system component needs a structured threat analysis before going to production.
Conduct a STRIDE threat model analysis for the following system: System name: [feature or component name] Description: [what the system does, 2-3 sentences] Architecture: - Components: [list: web app, API gateway, microservice A, database, message queue, external API, etc.] - Data flows: [describe how data moves: user -> LB -> API -> DB, API -> queue -> worker -> S3] - Trust boundaries: [internet/DMZ, DMZ/internal, service-to-service, cross-account] - Authentication: [OAuth2, API keys, mTLS, IAM roles] - Data classification: [PII, financial, health, public, internal] For each component and data flow, analyse all six STRIDE categories: - **S**poofing - Can an attacker impersonate a legitimate user/service? - **T**ampering - Can data be modified in transit or at rest? - **R**epudiation - Can actions be performed without an audit trail? - **I**nformation Disclosure - Can sensitive data leak? - **D**enial of Service - Can the service be overwhelmed? - **E**levation of Privilege - Can an attacker gain higher access? For each identified threat, provide: 1. Threat ID (T-001, T-002, ...) 2. STRIDE category 3. Affected component/data flow 4. Risk rating (Critical/High/Medium/Low) with likelihood and impact justification 5. Existing controls (if any) 6. Recommended mitigations with implementation priority 7. Residual risk after mitigation Output as a structured table followed by a prioritised mitigation plan.
Pro Tip: Feed the output into your design review document. Ask Claude to generate the architecture diagram description for draw.io/Lucidchart showing trust boundaries.

Security Architecture Review

As Needed
When reviewing a proposed system design for security gaps before approving it for implementation.
Review this system design for security concerns: System: [system name and purpose] Design document / architecture: ``` [paste architecture description, diagram-as-text, or design doc excerpt] ``` Cloud provider: [AWS / GCP / Azure / multi-cloud] Compliance requirements: [SOC2 / ISO27001 / HIPAA / PCI-DSS / FedRAMP / none specific] Data sensitivity: [PII, financial, health records, intellectual property, public] Review against these security domains: 1. **Network Security** - segmentation, private subnets, WAF, DDoS protection, VPC endpoints 2. **Encryption** - TLS version and cipher suites in transit, encryption at rest (KMS key management, envelope encryption), certificate management 3. **Authentication & Authorisation** - identity provider, token handling, session management, RBAC/ABAC design 4. **Data Protection** - classification, retention, backup encryption, cross-region replication security, data masking 5. **Logging & Monitoring** - audit trail completeness, SIEM integration, anomaly detection, log tampering protection 6. **Secrets Management** - how secrets are stored, rotated, injected (no hardcoded credentials) 7. **Supply Chain** - dependency scanning, container image provenance, SBOM generation 8. **Resilience** - failure modes that could become security incidents, blast radius containment For each finding, provide: severity, specific concern, recommended fix, and reference to the relevant security standard or best practice.

Zero Trust Network Design

Per Project
When designing or migrating to a zero-trust architecture where no network location is inherently trusted.
Design a zero-trust architecture for [environment/application name] on [AWS / GCP / Azure]. Current state: - Network: [traditional VPC with public/private subnets, VPN for remote access, peered VPCs, etc.] - Identity: [Active Directory, Okta, Google Workspace, AWS SSO] - Workloads: [Kubernetes, VMs, serverless, SaaS integrations] - Remote access: [VPN, SSH bastion, RDP, current pain points] - Users: [number of users, roles: developers, ops, contractors, third-party vendors] Design a zero-trust architecture covering: 1. **Identity-Aware Proxy** - replace VPN with [BeyondCorp / Zscaler / Cloudflare Access / Azure AD App Proxy], context-aware access policies (device posture, location, risk score) 2. **Micro-Segmentation** - network policies per workload, service mesh with mTLS ([Istio / Linkerd / Cilium]), deny-all default with explicit allow rules 3. **Mutual TLS (mTLS)** - certificate authority design, SPIFFE/SPIRE for workload identity, certificate rotation automation 4. **Continuous Verification** - re-authentication triggers (time-based, anomaly-based), step-up authentication for sensitive operations, session duration limits 5. **Device Trust** - endpoint compliance checks, managed vs. unmanaged device policies, certificate-based device identity 6. **Data-Centric Security** - encryption tied to identity, DLP policies at egress points, field-level encryption for sensitive data Include a migration plan (phases, quick wins, dependencies) and the policy engine decision flow for access requests.
Pro Tip: Start with one high-value application as a pilot, then expand. Ask Claude to create the phased rollout plan with success metrics for each phase.
📋 Compliance & Governance

Compliance Gap Analysis

Quarterly
When preparing for an audit or assessing your current security posture against a compliance framework.
Perform a compliance gap analysis mapping our current security controls against [SOC 2 Type II / ISO 27001 / NIST 800-53 / CIS Benchmarks / PCI-DSS v4.0 / HIPAA]. Our current controls: ``` [paste a summary of existing security controls, policies, tools in use, or a previous audit report excerpt] ``` Cloud environment: [AWS / GCP / Azure] with [list key services: EKS, RDS, S3, CloudTrail, GuardDuty, etc.] Organisation size: [employees, engineering team size] Current certifications: [list any existing certifications] For each framework control domain, provide: 1. **Control requirement** (ID and description from the framework) 2. **Current state** (Implemented / Partially Implemented / Not Implemented / Not Applicable) 3. **Existing evidence** (what tool/process satisfies this today) 4. **Gap description** (what is missing or insufficient) 5. **Remediation action** (specific steps to close the gap) 6. **Priority** (Critical / High / Medium / Low based on audit risk) 7. **Estimated effort** (days/weeks and team responsible) Output as a table, then provide an executive summary with the top 10 gaps to address before the next audit cycle.

Security Policy Writer

As Needed
When you need to draft or update a formal security policy that meets industry standards and is actually usable by your team.
Draft a [Data Classification / Acceptable Use / Incident Response / Access Management / Encryption / Vulnerability Management / Change Management] policy for our organisation. Context: - Industry: [technology, finance, healthcare, government, etc.] - Compliance frameworks: [SOC2, ISO27001, NIST, HIPAA, PCI-DSS] - Organisation size: [approximate headcount] - Cloud provider(s): [AWS / GCP / Azure / hybrid] - Existing related policies: [list any policies this should align with] The policy must include: 1. **Purpose and Scope** - what this policy covers and who it applies to 2. **Definitions** - key terms used in the policy 3. **Policy Statements** - clear, actionable requirements (not vague aspirational language) 4. **Roles and Responsibilities** - who is accountable for what (RACI where appropriate) 5. **Standards and Procedures** - specific technical requirements (minimum password length, encryption algorithms, retention periods, etc.) 6. **Exceptions Process** - how to request and document policy exceptions 7. **Enforcement** - consequences of non-compliance 8. **Review Cycle** - how often this policy is reviewed and by whom 9. **References** - mapped to specific framework controls (e.g., SOC2 CC6.1, ISO 27001 A.9.2) Tone: authoritative but readable. Avoid legalese. Each requirement should be testable/auditable.
Pro Tip: After generating the policy, ask Claude to create a one-page summary for employee training and a compliance checklist for auditors.

Audit Evidence Collector

As Needed
When an audit is approaching and you need to systematically gather evidence for each control requirement.
Generate an evidence collection checklist for our upcoming [SOC 2 Type II / ISO 27001 / PCI-DSS / HIPAA / FedRAMP] audit. Audit details: - Audit period: [start date] to [end date] - Scope: [systems, services, and processes in scope] - Cloud environment: [AWS / GCP / Azure] - Previous audit findings: [list any open items from last audit] For each control domain in scope, provide: 1. **Control ID and Name** (from the framework) 2. **Evidence Required** (specific artifacts: screenshots, exports, configurations, logs) 3. **Source** (where to obtain the evidence: AWS Console, Terraform state, Jira, Confluence, HR system) 4. **CLI Command or Export Steps** (exact commands to extract the evidence, e.g., aws cloudtrail describe-trails, kubectl get networkpolicies -A) 5. **Control Narrative** (a 2-3 sentence description of how we satisfy this control, written in audit-ready language) 6. **Evidence Owner** (which team is responsible for collecting this) 7. **Status** (placeholder for tracking: Not Started / In Progress / Collected / Reviewed) Group by control domain and include a timeline suggesting when to start collecting each category of evidence. Flag any controls where evidence collection is typically difficult or time-consuming.
🚨 Vulnerability Management & Incident Response

Vulnerability Assessment Report

Weekly
When processing vulnerability scan output and you need a prioritised, actionable remediation plan instead of a raw findings dump.
Analyse this vulnerability scan output and create a prioritised remediation plan: Scan source: [Qualys / Nessus / Trivy / Snyk / AWS Inspector / Dependabot] Scan scope: [production containers / EC2 fleet / application dependencies / cloud infrastructure] Scan results: ``` [paste vulnerability scan output: CVE IDs, severity, affected packages, CVSS scores] ``` Environment context: - Internet-facing: [yes/no, which components] - Data sensitivity: [PII, financial, health, internal only] - Compensating controls: [WAF, network segmentation, runtime protection] For each vulnerability, assess: 1. **CVE ID and Description** 2. **CVSS Score** and your **adjusted risk rating** (considering exploitability, exposure, and compensating controls) 3. **Affected assets** (which services/images/hosts) 4. **Exploitability** - is there a known exploit in the wild? Is it in CISA KEV? 5. **Remediation** - specific package upgrade, patch, or configuration change with the exact command 6. **SLA** - Critical: 48hrs, High: 7 days, Medium: 30 days, Low: 90 days (adjust based on context) 7. **Workaround** - if an immediate patch is not available, what mitigates the risk? Output: - Executive summary (total findings by severity, trend vs. last scan) - Prioritised remediation table sorted by adjusted risk - Exceptions list (vulnerabilities accepted with justification) - Metrics: mean time to remediate by severity, ageing vulnerabilities

Security Incident Response Plan

Per Incident
When you need to create or update an incident response plan for a specific threat scenario your organisation faces.
Create a security incident response plan for the following threat scenario: Scenario: [data breach via compromised API key / compromised developer credentials / ransomware on build server / cryptominer in Kubernetes / supply chain attack via malicious dependency / insider threat / DDoS attack] Environment: - Cloud: [AWS / GCP / Azure] - Infrastructure: [Kubernetes, serverless, VMs] - Sensitive data: [types of data at risk: PII, credentials, source code, financial] - Team size: [security team size, on-call structure] - Existing tools: [SIEM, EDR, SOAR, cloud-native security tools] Structure the plan as: 1. **Detection & Identification** - What alerts/indicators signal this scenario? (GuardDuty findings, CloudTrail anomalies, SIEM rules) 2. **Severity Classification** - Criteria for P1/P2/P3, escalation thresholds 3. **Containment (Immediate - first 30 minutes)** - Short-term containment actions (isolate, revoke, block) with exact commands - Evidence preservation steps (snapshot, log export, memory dump) - Do NOT list (actions that could destroy evidence or worsen the situation) 4. **Eradication** - Remove the threat actor/malware, patch the entry point, rotate all potentially compromised credentials 5. **Recovery** - Restore from known-good state, staged reconnection, enhanced monitoring period 6. **Communication Plan** - Internal: who to notify at each severity level (RACI matrix) - External: customer notification templates, regulatory reporting requirements ([GDPR 72-hour rule / state breach laws / PCI]) - Legal: when to engage legal counsel 7. **Post-Incident** - forensic analysis, lessons learned, control improvements 8. **Tabletop Exercise** - scenario script to rehearse this plan with the team
Pro Tip: Run a tabletop exercise with the generated scenario quarterly. Ask Claude to play the role of the attacker and inject realistic curveballs during the exercise.

Cloud Security Posture Review

Monthly
When you have security tool output (Security Hub, Prowler, ScoutSuite) and need to turn it into a prioritised action plan.
Audit the following cloud security posture findings and create a prioritised remediation backlog: Source: [AWS Security Hub / Prowler / ScoutSuite / Azure Defender / GCP Security Command Center] Findings: ``` [paste security findings: finding ID, severity, resource, description, compliance standard] ``` Environment: - Accounts/projects in scope: [list account IDs or project names] - Workload types: [production, staging, development, sandbox] - Previous review date: [date of last review] Analyse and provide: 1. **Executive Dashboard** - Total findings by severity (Critical/High/Medium/Low/Informational) - Trend comparison with previous review (new, resolved, unchanged) - Compliance score by framework (CIS, AWS FSBP, PCI) 2. **Critical & High Findings (Detailed)** - For each: finding, affected resource, risk explanation in business terms, exact remediation steps (CLI commands or Terraform code), owner assignment - Flag any findings that indicate active compromise or immediate data exposure risk 3. **Categorised Backlog** - Group by domain: IAM, Network, Encryption, Logging, Storage, Compute - For each group: count, effort estimate, recommended sprint allocation 4. **Quick Wins** - findings fixable in under 1 hour with high security impact (e.g., enable S3 block public access, enable CloudTrail log validation, restrict security group) 5. **Exceptions & Accepted Risks** - findings that should be suppressed with documented justification 6. **Automation Recommendations** - findings that should be auto-remediated via [AWS Config Rules / Cloud Custodian / Azure Policy / GCP Organisation Policy]
