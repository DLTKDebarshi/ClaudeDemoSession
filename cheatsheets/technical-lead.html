🛠 Architecture & Design

Architecture Decision Record (ADR)

As Needed

Draft an ADR with context, decision, consequences, and alternatives considered for a technical choice.

Write an Architecture Decision Record (ADR) for the following technical decision. Title: [e.g. ADR-042: Adopt GraphQL Federation for API Gateway] Context: - Problem: [e.g. Our 12 microservices each expose REST APIs; clients make 4-7 calls per page load, causing latency and tight coupling] - Current state: [e.g. REST APIs behind Kong gateway, BFF pattern partially implemented] - Constraints: [e.g. must support existing mobile clients during migration, team has limited GraphQL experience] - Stakeholders consulted: [e.g. frontend team, platform team, security] Alternatives considered: 1. [e.g. Keep REST + expand BFF layer] 2. [e.g. Adopt GraphQL monolithic gateway] 3. [e.g. Adopt GraphQL Federation (Apollo)] Format the ADR as: 1. Status (proposed/accepted/deprecated) 2. Context (the problem and why we need to decide now) 3. Decision (what we chose and why) 4. Alternatives considered (with pros/cons for each) 5. Consequences (positive, negative, and neutral) 6. Migration plan (high-level steps) 7. Review date (when we'll revisit this decision) Follow the Michael Nygard ADR format. Keep each section concise.
Pro Tip: Store ADRs in your repo under docs/adr/ and number them sequentially for a searchable decision log.

System Design Document (RFC)

As Needed

Create a structured RFC/design doc for a new feature or system with diagrams description, trade-offs, and migration plan.

Write a technical design document (RFC) for the following system/feature. Title: [e.g. Real-time Notification Service] Author: [your name] Reviewers: [list of reviewers] Problem statement: [e.g. Users currently discover status changes only on page refresh. We need real-time push notifications for order updates, mentions, and system alerts across web and mobile.] Requirements: - Functional: [e.g. deliver notifications within 2 seconds, support web push + mobile push + in-app, user preference management] - Non-functional: [e.g. 99.9% delivery rate, support 50K concurrent connections, <100ms server-side processing] - Out of scope: [e.g. email notifications, SMS, notification analytics] Current system context: [e.g. monolithic Django app, PostgreSQL, Redis for caching, deployed on EKS] Structure the RFC as: 1. Summary (1 paragraph) 2. Motivation and goals 3. Proposed architecture (describe components, data flow, and interactions so a diagram could be drawn) 4. API design (key endpoints/events with request/response shapes) 5. Data model (key entities and storage choices) 6. Trade-offs and alternatives rejected 7. Security considerations 8. Observability and monitoring plan 9. Migration / rollout strategy (feature flags, canary, etc.) 10. Open questions for reviewers 11. Timeline estimate (phases with milestones)

Technical Debt Assessment

Quarterly

Audit codebase/system areas for tech debt, categorise by severity, estimate remediation effort, and prioritise.

Conduct a technical debt assessment for our [service name / codebase / system area]. Known debt items (paste what you have, I'll help structure them): [e.g. - Auth service still uses deprecated JWT library (security risk) - Order processing has no retry logic (causes silent failures) - Test coverage for payment module is 23% (regression risk) - Database queries in user service are N+1 (performance) - Deployment takes 45 minutes due to monolithic build (velocity)] Additional context: - Team size working on this area: [e.g. 4 engineers] - Upcoming feature work that may be affected: [e.g. payment provider migration in Q3] - Recent incidents caused by debt: [e.g. 2 outages in last quarter from retry logic gaps] For each debt item, provide: 1. Category (security, reliability, performance, maintainability, developer experience) 2. Severity (critical / high / medium / low) with justification 3. Business risk if left unaddressed 4. Estimated remediation effort (T-shirt size + approximate days) 5. Dependencies and prerequisites Then produce: - Prioritised remediation backlog (ordered by risk-adjusted ROI) - Recommended allocation: what % of sprint capacity to dedicate to debt - Quick wins (can be done in <2 days) vs strategic investments - Suggested pitch to product stakeholders for the top 3 items
Pro Tip: Pair this with static analysis reports (SonarQube, CodeClimate) for a data-backed assessment.
🔍 Code Quality & Reviews

Code Review Checklist Generator

Per Project

Create a tailored code review checklist based on the project's tech stack, known problem areas, and team standards.

Generate a code review checklist tailored to our project. Tech stack: [e.g. TypeScript, React 18, Node.js, PostgreSQL, GraphQL, deployed on AWS ECS] Testing framework: [e.g. Jest + React Testing Library + Playwright for E2E] Known problem areas: [e.g. inconsistent error handling, missing input validation on API layer, memory leaks in WebSocket connections] Team standards: [e.g. all public APIs must have OpenAPI spec, minimum 80% test coverage on new code, no direct DB queries outside repository layer] Create a checklist organised by: 1. Correctness (logic errors, edge cases, error handling) 2. Security (injection, auth, data exposure, input validation) 3. Performance (N+1 queries, unnecessary re-renders, memory leaks, bundle size) 4. Maintainability (naming, complexity, DRY, single responsibility) 5. Testing (coverage, edge cases, mocking strategy, test readability) 6. Documentation (inline comments for complex logic, API docs, changelog) 7. Project-specific items (based on our known problem areas above) Format each item as a yes/no checklist question. Include "why it matters" for non-obvious items. Mark items as [MUST] vs [SHOULD] priority.

Pull Request Review Summary

Daily

Analyse a PR diff and provide a structured review: correctness concerns, performance implications, security issues, and style notes.

Review the following pull request diff and provide structured feedback. PR Title: [e.g. Add rate limiting middleware to API gateway] PR Description: [paste the PR description] Files changed: [number] Diff: [Paste the git diff or key changed files here] Context: - This PR is for: [e.g. production API service handling 10K req/min] - Related ticket: [e.g. JIRA-1234] Provide review organised as: 1. Summary: What this PR does in 2-3 sentences 2. Correctness: Logic issues, edge cases not handled, potential bugs 3. Security: Injection risks, auth gaps, data exposure, input validation 4. Performance: Scaling concerns, query efficiency, memory usage, caching opportunities 5. Style & maintainability: Naming, complexity, duplication, readability 6. Testing gaps: What tests are missing or insufficient 7. Approval recommendation: Approve / Request Changes / Needs Discussion For each finding, reference the specific file and line. Classify as: [BLOCKER] [CONCERN] [NIT] [PRAISE]
Pro Tip: Use git diff main...feature-branch to get the full diff and paste it directly.

Production Bug Root Cause Analysis

As Needed

Guide a structured RCA for a production issue: timeline reconstruction, root cause identification, and prevention measures.

Help me conduct a root cause analysis for a production bug. Bug summary: [e.g. Intermittent 500 errors on /api/orders endpoint, affecting ~5% of requests during peak hours] What we know so far: - First reported: [date/time] - Affected services: [e.g. order-service, payment-service] - Error messages/logs: [paste relevant log snippets] - Recent changes: [e.g. deployed v2.4.1 two days ago, added connection pooling config change] - Workaround applied: [e.g. increased replica count from 3 to 6, which reduced error rate] - What we've ruled out: [e.g. database is healthy, network latency is normal] Guide me through: 1. Timeline reconstruction (key events in chronological order) 2. 5 Whys analysis (drill from symptom to root cause) 3. Contributing factors (what conditions made this possible) 4. Hypotheses ranked by likelihood with evidence for/against each 5. Verification steps to confirm the root cause 6. Immediate fix vs proper fix (with trade-offs) 7. Prevention measures (code, process, monitoring) to stop recurrence 8. Detection improvements (what alerts/monitors should we add) Format as a formal RCA document that can be shared with the team.
📋 Technical Communication

Technical Spike Summary

Weekly

Synthesise research findings from a technical spike into a recommendation with evidence, risks, and next steps.

Synthesise my technical spike findings into a clear recommendation document. Spike objective: [e.g. Evaluate whether we should migrate from REST to gRPC for inter-service communication] Time spent: [e.g. 3 days] What I investigated: [e.g. - Benchmarked gRPC vs REST for our top 5 inter-service call patterns - Prototyped gRPC implementation for order-service to inventory-service - Evaluated team learning curve (surveyed 4 engineers) - Reviewed gRPC ecosystem maturity for our stack (Node.js + Python)] Raw findings: [Paste your notes, benchmark results, pros/cons lists, etc.] Structure as: 1. Executive summary (1 paragraph: question asked, answer found) 2. Background (why we investigated this) 3. Methodology (what we tested and how) 4. Key findings (with data/evidence, not just opinions) 5. Recommendation (go / no-go / defer, with clear reasoning) 6. Risks and mitigations if we proceed 7. Estimated effort to implement 8. Next steps and decision needed from the team Keep it factual and concise. Flag where findings are based on limited data vs strong evidence.

Non-Technical Stakeholder Explanation

As Needed

Translate a complex technical decision or trade-off into plain language for PMs, leadership, or business stakeholders.

Translate the following technical concept into plain language for non-technical stakeholders. Technical topic: [e.g. Why we need to migrate from a monolithic database to a distributed database architecture] Technical details: [e.g. Our single PostgreSQL instance is hitting connection limits at 500 concurrent connections. Write throughput is capped at 15K TPS. We need to shard the database, which means splitting data across multiple database servers. This requires changing how we write queries and adding a routing layer.] Audience: [e.g. VP of Product, CFO, non-technical project managers] Key decision they need to make: [e.g. approve 6 weeks of engineering time and $30K additional infra cost] Produce: 1. Plain-language explanation (use analogies, avoid all jargon) 2. Why this matters to the business (in their terms: revenue, customers, speed) 3. What happens if we do this (benefits, timeline, cost) 4. What happens if we don't (risks, timeline to failure) 5. The trade-offs in simple terms 6. The specific ask (decision, budget, timeline approval) Rules: No acronyms without explanation. No technical terms. Use analogies from everyday business. Max 1 page.
Pro Tip: Ask Claude to role-play as the stakeholder and poke holes in the explanation before you send it.

Engineering Blog Post / Knowledge Share

Monthly

Draft an internal knowledge-sharing post about a technical challenge, solution, and lessons for the wider engineering org.

Draft an internal engineering blog post / knowledge share article. Topic: [e.g. How we reduced API latency by 60% by fixing our caching strategy] Details: - The problem we faced: [e.g. p95 latency on product listing API climbed from 200ms to 800ms over 3 months] - What we tried that didn't work: [e.g. added more replicas, optimised DB queries, both helped marginally] - The root cause we discovered: [e.g. cache stampede during TTL expiry on popular items] - The solution: [e.g. implemented stale-while-revalidate pattern with probabilistic early expiration] - The results: [e.g. p95 dropped to 150ms, cache hit rate improved from 72% to 94%] Structure as: 1. Catchy title and TL;DR (3 bullet points) 2. The problem (with metrics and why it mattered) 3. Investigation journey (what we tried, what we learned) 4. The solution (with enough technical detail for others to replicate) 5. Results (before/after metrics, graphs description) 6. Lessons learned (what we'd do differently) 7. When to apply this pattern (and when not to) Tone: conversational, educational, honest about mistakes. Target audience: mid-level engineers across the org. Length: 800-1200 words.
💪 Mentoring & Standards

Engineering Standards Guide

Quarterly

Draft or update team engineering standards covering coding conventions, testing requirements, CI/CD expectations, and documentation norms.

Draft (or update) our team's engineering standards guide. Team context: - Tech stack: [e.g. TypeScript/Node.js backend, React frontend, PostgreSQL, Redis, AWS] - Team size: [e.g. 12 engineers, mix of mid and senior] - Current pain points: [e.g. inconsistent error handling patterns, PRs with no tests getting merged, deploy rollbacks due to missing feature flags] - Existing standards (if updating): [paste current doc or summarise what exists] Cover these areas: 1. Code conventions (naming, file structure, error handling patterns, logging standards) 2. Testing requirements (minimum coverage, what must be tested, testing pyramid expectations) 3. PR standards (size limits, description template, review turnaround SLA, approval requirements) 4. CI/CD expectations (what must pass before merge, feature flag requirements, rollback procedures) 5. API design standards (versioning, error response format, pagination, auth patterns) 6. Documentation norms (what needs docs, where they live, when to update) 7. Observability standards (what to log, metric naming conventions, alert thresholds) 8. Security baseline (dependency scanning, secret management, input validation) For each standard: - State the rule clearly - Explain the "why" behind it (not just the "what") - Provide a good and bad example where applicable - Note any exceptions or escape hatches Tone: authoritative but pragmatic. These are guardrails, not bureaucracy.
Pro Tip: Turn each section into a PR template checklist item so standards are enforced at review time.

Technical Interview Question Bank

Per Hire

Generate role-specific technical interview questions with scoring rubrics for system design, coding, and architecture rounds.

Generate a technical interview question bank for a [role, e.g. Senior Backend Engineer] position. Role details: - Level: [e.g. Senior / Staff / Principal] - Primary tech stack: [e.g. Python, Django, PostgreSQL, AWS, Kubernetes] - Key responsibilities: [e.g. design and build core platform services, mentor 2-3 junior engineers, own system reliability] - Team they're joining: [e.g. Payments team, handling $2M daily transaction volume] Generate questions for each interview round: 1. System Design (45 min): - 2 design questions relevant to our domain with follow-up probes - Scoring rubric: what good/great/exceptional answers look like 2. Coding (45 min): - 2 coding problems (one algorithmic, one practical/domain-relevant) - Expected approach, optimal solution, and common pitfalls - Scoring rubric with signal indicators 3. Architecture Deep-Dive (30 min): - 3 questions about past experience with architectural decisions - Red flags and green flags to listen for 4. Technical Communication (15 min): - 2 questions testing ability to explain complex concepts simply For each question include: - The question text - What signal you're testing for - Scoring rubric (1-4 scale with descriptions) - Follow-up questions to probe deeper - Time allocation

Developer Onboarding Technical Guide

Per Hire

Create a technical onboarding guide covering codebase architecture, local dev setup, key services, and common debugging workflows.

Create a technical onboarding guide for a new engineer joining our team. System overview: - Product: [e.g. B2B SaaS platform for project management] - Architecture: [e.g. 15 microservices, event-driven, deployed on EKS] - Key services: [list main services and their responsibilities] - Tech stack: [e.g. TypeScript, React, Node.js, PostgreSQL, Redis, Kafka, AWS] - Repo structure: [e.g. monorepo / polyrepo, key repo names] Local dev requirements: - OS: [e.g. macOS, supported versions] - Required tools: [e.g. Docker, Node 20, pnpm, AWS CLI, kubectl] - Key config: [e.g. env vars needed, VPN setup, SSO access] Structure the guide as: 1. Week 1: Getting Set Up - Local environment setup (step-by-step with verification commands) - Access requests checklist (repos, AWS, monitoring, CI/CD, Slack channels) - Run the app locally and verify end-to-end - First PR: fix a "good first issue" to learn the workflow 2. Week 2: Understanding the System - Architecture overview (service map with data flow) - Key databases and their schemas - How requests flow from user to backend and back - Important design patterns used in the codebase 3. Week 3-4: Going Deeper - Common debugging workflows (how to trace a request, read logs, check metrics) - Deployment process (how code gets to production) - On-call expectations and runbooks location - Key domain concepts the engineer needs to understand 4. Reference section - Glossary of team-specific terms - Key contacts (who owns what) - Useful links (dashboards, docs, runbooks, architecture diagrams) Write it as if explaining to a strong engineer who is new to the codebase, not new to engineering.
Pro Tip: Have a recent hire review the guide and flag anything confusing before publishing.
