🚀 CI/CD & Pipelines

CI/CD Pipeline Builder

As Needed
When you are setting up a new service or migrating an existing pipeline and need a production-ready configuration with all stages wired correctly.
Generate a complete CI/CD pipeline configuration for [GitHub Actions / GitLab CI / Jenkins] that builds, tests, scans, and deploys [service name] written in [language/framework]. Requirements: - Source repo: [repo URL or mono-repo path] - Environments: [dev, staging, production] - Build: compile/package the application and produce a Docker image tagged with git SHA - Test: run unit tests, integration tests, and report coverage (fail if below [coverage threshold, e.g. 80%]) - Scan: include SAST (Semgrep/SonarQube) and container image scanning (Trivy/Snyk) - Deploy: deploy to [EKS / GKE / ECS / Azure AKS] with environment promotion gates - Notifications: send results to [Slack channel / Teams webhook] Include caching for dependencies, parallelised stages where possible, and environment-specific variable handling. Add comments explaining each stage.
Pro Tip: Ask Claude to also generate the branch protection rules and required status checks that complement this pipeline.

Deployment Strategy Designer

As Needed

Design a [blue-green / canary / rolling] deployment strategy for [service name] running on [Kubernetes / ECS / Lambda / VMs]. Context: - Current traffic: [requests per second] - SLA requirement: [e.g. 99.95% uptime] - Deployment frequency: [e.g. 3x per week] - Database changes involved: [yes/no, describe migration approach] Please include: 1. Automated rollback triggers (what metrics/conditions trigger rollback) 4. Rollback procedure with estimated recovery time 5. Smoke test suite to run at each traffic shift stage 6. Communication plan (who gets notified at each stage) Output as a runbook with commands/configurations I can implement directly.

Pipeline Troubleshooter

Daily
When a CI/CD pipeline has failed and you need to quickly diagnose the root cause from error logs.
My CI/CD pipeline for [service name] on [GitHub Actions / GitLab CI / Jenkins] is failing. Help me diagnose the issue. Failed stage: [build / test / scan / deploy] Error log (last 50 lines): ``` [paste error log output here] ``` Recent changes: - [describe recent code/config changes, dependency updates, or infra changes] Environment: [OS, runtime version, container base image] Please: 1. Identify the root cause from the error output 2. Explain WHY this error occurred (not just what it means) 3. Provide the exact fix with code/config changes 4. Suggest a preventive measure (linting rule, pre-commit hook, or pipeline guard) so this class of error does not recur 5. If this could be a flaky/intermittent issue, explain how to confirm and add retry logic
Pro Tip: Paste the full log output, not just the error line. Context around the failure often reveals the real cause.
📦 Containers & Orchestration

Dockerfile Optimiser

As Needed
When you have a working Dockerfile but want to reduce image size, improve build speed, and harden it for production.
Review and optimise this Dockerfile for production readiness: ```dockerfile [paste your Dockerfile here] ``` Application details: - Language/Runtime: [e.g. Node 20, Python 3.12, Go 1.22, Java 21] - Current image size: [e.g. 1.2 GB] - Build time: [e.g. ~8 minutes] Please optimise for: 1. **Image size** - multi-stage build, minimal base image (distroless/alpine), remove unnecessary files 2. **Build cache** - order layers for maximum cache reuse, separate dependency install from code copy 3. **Security** - non-root user, no secrets in layers, minimal packages, specific version pins 4. **Best practices** - .dockerignore recommendations, HEALTHCHECK instruction, proper signal handling (tini/dumb-init) Provide the optimised Dockerfile with comments explaining each change and the expected size/build-time improvement.

As Needed
When deploying a new microservice to Kubernetes and you need a complete set of production-grade manifests.

Specifications: - Container image: [registry/image:tag] - Port: [e.g. 8080] - Resource requirements: CPU [request/limit, e.g. 250m/500m], Memory [request/limit, e.g. 256Mi/512Mi] - Expected replicas: [min / max, e.g. 3 / 10] - Environment variables: [list key env vars or ConfigMap/Secret names] - External access: [yes/no, domain name if yes] - Namespace: [namespace name] Generate these manifests with best practices: 1. **Deployment** - rolling update strategy, pod anti-affinity, topology spread, security context (non-root, read-only rootfs) 2. **Service** - ClusterIP with named ports 3. **Ingress** - TLS, path routing, annotations for [nginx / ALB / GCE] ingress controller 4. **HPA** - scale on CPU and custom metrics 5. **PDB** - ensure availability during node drains 6. **NetworkPolicy** - restrict ingress/egress to required services only 7. **ServiceAccount** - with IAM role annotation for [AWS IRSA / GCP Workload Identity] Include readiness and liveness probes with sensible defaults. Output as separate YAML documents.
Pro Tip: Feed the output into a Kustomize base, then ask Claude to generate environment-specific overlays for dev/staging/prod.

📈 Monitoring & Observability

Alert Rule Designer

As Needed
When setting up alerting for a service and you need well-tuned rules that catch real problems without alert fatigue.
Design alerting rules for [service name] using [Prometheus/Alertmanager / Datadog / CloudWatch / PagerDuty]. Service profile: - Type: [API / worker / database / message queue / web frontend] - SLO targets: availability [e.g. 99.9%], latency p99 [e.g. < 500ms] - Traffic pattern: [steady / bursty / cron-driven / business-hours only] - Dependencies: [list downstream services and data stores] For each alert, provide: 1. Alert name and severity (critical / warning / info) 2. PromQL / query expression with appropriate aggregation window 3. Threshold and rationale for why this threshold was chosen 4. For/pending duration to avoid flapping 5. Labels and annotations (summary, description, runbook_url, dashboard_url) 6. Routing (who gets paged vs. who gets a Slack notification) Include alerts for: error rate, latency degradation, saturation (CPU/memory/disk/connections), dependency failures, and SLO burn rate. Explain which alerts should wake someone up at 3 AM vs. which can wait until morning.
Pro Tip: Ask Claude to also generate the Alertmanager routing config or Datadog notification rules to match these alerts.

Service details: - Type: [API service / background worker / data pipeline / web app] - Tech stack: [language, framework, database, message queue, cache] - Key business function: [what does this service do for users?] Create a dashboard with these sections: 1. **Overview row** - service health status, uptime %, active instances, current deployment version 2. **Golden Signals** - latency (p50/p95/p99), traffic (RPS), error rate (%), saturation (CPU/memory/connections) 3. **Business Metrics** - [e.g. orders processed, messages delivered, API calls by customer] 4. **Dependencies** - response time and error rate for each downstream service and data store 5. **Infrastructure** - pod/instance count, node health, disk I/O, network throughput For each panel, specify: - Query/metric expression - Visualisation type (graph, gauge, stat, table, heatmap) - Appropriate time range and refresh interval - Threshold colours (green/yellow/red) and their values

🚨 Incidents & Automation

Incident Response Runbook

Per Service
When you need a structured, copy-pasteable runbook that any on-call engineer can follow during an outage.
Create an incident response runbook for [service name] when [failure scenario, e.g. "the database connection pool is exhausted" / "API latency exceeds 5 seconds" / "message queue consumer lag exceeds 1 million"]. Service context: - Architecture: [brief description of service and its dependencies] - Infrastructure: [AWS/GCP/Azure, Kubernetes/ECS, region] - On-call team: [team name] Structure the runbook as: 1. **Detection** - Which alerts fire? What dashboards to check first? 2. **Severity Assessment** - How to determine if this is SEV1/SEV2/SEV3 (user impact criteria) 3. **Immediate Triage** (first 5 minutes) - Commands to run, metrics to check, quick mitigations 4. **Diagnosis** - Decision tree: "If X, check Y. If Y shows Z, then..." 5. **Remediation** - Step-by-step fix procedures with exact commands 6. **Rollback** - How to revert if remediation makes things worse 7. **Communication** - Status page update templates, stakeholder notification messages 8. **Post-resolution** - Verification checks, monitoring to watch for recurrence Include actual commands (kubectl, aws cli, curl) with placeholders, not just descriptions.
Pro Tip: Store runbooks alongside the service code in a /runbooks directory and link them from your alert annotations.

Post-Incident Review (PIR)

Per Incident
When an incident is resolved and you need to transform messy notes into a structured, blameless review document.
Transform these raw incident notes into a structured, blameless post-incident review. Incident ID: [INC-XXXX] Severity: [SEV1 / SEV2 / SEV3] Duration: [start time] to [end time] ([total duration]) Services affected: [list services] User impact: [e.g. "15% of API requests returned 500 for 45 minutes"] Raw timeline and notes: ``` [paste Slack messages, notes, timestamps, and actions taken during the incident] ``` Generate a PIR with: 1. **Executive Summary** (3 sentences: what happened, impact, resolution) 2. **Timeline** (clean, timestamped sequence of events: detection, escalation, diagnosis, mitigation, resolution) 3. **Root Cause** (technical root cause with evidence) 4. **Contributing Factors** (systemic issues: missing alerts, insufficient testing, unclear ownership, documentation gaps) 5. **What Went Well** (things that helped resolve the incident faster) 6. **What Could Be Improved** (process and tooling gaps) 7. **Action Items** (table: action, owner, priority, due date) - focus on systemic fixes, not "be more careful" 8. **Lessons Learned** (key takeaways for the wider engineering org) Tone: blameless and constructive. Focus on systems and processes, not individuals.

Automation Script Designer

As Needed
When you want to automate a repetitive operational task with a robust, production-quality script.
Design a [Bash / Python] automation script for: [describe the task, e.g. "rotate database credentials and update Kubernetes secrets" / "clean up ECR images older than 30 days" / "generate a daily cost report from AWS Cost Explorer"]. Requirements: - Environment: [Linux distro, cloud provider, available CLI tools] - Trigger: [cron schedule / on-demand / event-driven] - Inputs: [parameters the script needs: account IDs, region, thresholds, etc.] - Notifications: [Slack webhook / email / SNS topic for success/failure alerts] The script must include: 1. **Argument parsing** with help text and validation 2. **Dry-run mode** (-n/--dry-run) that shows what would happen without making changes 3. **Idempotency** - safe to run multiple times without side effects 4. **Error handling** - set -euo pipefail (bash) or try/except with proper exit codes 5. **Logging** - timestamped structured output with configurable verbosity 6. **Lock file** - prevent concurrent execution if applicable 7. **Rollback** - undo partial changes on failure 8. **Exit summary** - report what was done (items processed, errors, duration) Include inline comments, a usage example, and a cron entry if scheduled.
Pro Tip: Ask Claude to also generate a unit test file and a CI pipeline step that validates the script with ShellCheck or pytest.
