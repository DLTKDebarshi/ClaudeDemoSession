SERVICE DEPENDENCY MAP — Order Management Domain
Last updated: April 2026

=== SERVICES ===

1. api-gateway (Kong)
   - Entry point for all external traffic
   - Routes to: order-service, product-catalog-svc, user-auth-svc
   - Rate limiting: 1000 req/sec per client
   - Health check: /healthz every 10s

2. order-service (Go, v2.14.0 → rolled back to v2.13.2)
   - Handles: order creation, order reads, order status updates
   - Depends on:
     → orders-db-primary (RDS PostgreSQL) — primary data store
     → orders-cache-01 (ElastiCache Redis) — read cache, 5-min TTL
     → product-catalog-svc — inventory validation on order create
     → payment-svc — payment processing on order create
     → notification-svc — async via SQS (order confirmation emails)
   - Replicas: 8 pods (HPA: min 4, max 16)
   - Connection pool to DB: max 25 per pod (8 pods × 25 = 200 total)

3. product-catalog-svc (Node.js, v3.2.1)
   - Handles: product search, category browse, inventory queries
   - Depends on:
     → catalog-db (RDS MySQL) — product data
     → catalog-cache (ElastiCache Redis) — search results cache
   - Replicas: 6 pods
   - NOTE: Was returning 503s during incident due to cascading backpressure from order-service

4. payment-svc (Java, v4.1.0)
   - Handles: payment authorization, capture, refund
   - Depends on:
     → Stripe API (external)
     → payment-db (RDS PostgreSQL)
   - Circuit breaker: trips at 50% error rate, 30s cooldown
   - NOT impacted during this incident

5. user-auth-svc (Go, v1.9.3)
   - Handles: JWT validation, session management
   - Depends on:
     → auth-db (RDS PostgreSQL)
     → auth-cache (ElastiCache Redis)
   - NOT impacted during this incident

6. notification-svc (Python, v2.0.4)
   - Handles: email, SMS, push notifications
   - Triggered via SQS queues (async)
   - Depends on:
     → SES (email), SNS (SMS), Firebase (push)
   - NOT directly impacted but order confirmation emails were delayed during incident

=== INFRASTRUCTURE ===

- Kubernetes: EKS 1.29, us-east-1, 3 AZs
- Database: RDS PostgreSQL 15.4 (db.r6g.2xlarge)
  - max_connections: 200 (hard limit)
  - Connection pooling: application-side (each pod gets 25)
  - Read replicas: 1 (orders-db-replica, used for reporting only, NOT by order-service)
- Cache: ElastiCache Redis 7.0, cluster mode, 3 shards × 1 replica
  - Max memory: 13GB per node
  - Eviction policy: allkeys-lru
- Load Balancer: ALB with WAF
- CDN: CloudFront (static assets only, not API traffic)
- CI/CD: GitHub Actions → ArgoCD (GitOps)
  - Canary deployments: available via Argo Rollouts but NOT enforced for all services
  - order-service v2.14.0 was deployed as a full rollout (no canary)
