Hands-On Lab 3

The Infrastructure Decision

Generate an Architecture Decision Record, Terraform module, security review, and cost projection for a cloud migration — four deliverables that normally take weeks, done in 15 minutes.

Scenario

The Migration Mandate

Leadership has mandated: migrate the Invoice Processing Service from on-prem to AWS by Q3 2026. The ABBYY OCR license renewal ($45K/year, 3-year lock-in) is due in July — if you don't migrate before then, you're locked in for $135K. The Cloud Architecture Board meets Thursday, and they need: an Architecture Decision Record (ADR) explaining the approach, a Terraform module skeleton for the core infrastructure, a security review against the compliance requirements, and a cost projection. Four deliverables. Three days. You've been doing this math in your head — let's get it on paper.

The Old Way

Schedule 4 separate meetings (architecture review, security review, IAC review, cost review). Draft each document in Google Docs. Collect feedback async. Takes 2–3 weeks.

The AI Way

Upload the current architecture and compliance requirements to Claude. Generate all four deliverables in 15 minutes. Bring drafts to the meetings instead of blank whiteboards.

Problem

What You Need to Deliver

Using the sample input files provided below, you will use Claude to create the following four deliverables:

  1. An Architecture Decision Record (ADR) — documenting the migration approach with alternatives considered
  2. A Terraform module skeleton — core infrastructure: VPC, ECS, RDS, S3 with security configurations
  3. A security compliance review — mapping the proposed architecture against the compliance requirements
  4. A cost projection — estimated monthly AWS costs vs current on-prem costs

Steps

How to Run This Lab

Follow these steps in order. Each step builds on the previous one, using the same Claude conversation thread throughout.

1

Open claude.ai

Go to claude.ai and start a new conversation. Make sure you're using Claude (Sonnet or Opus).

2

Upload the Data

Upload both files — sample-architecture-current.txt and sample-compliance-requirements.txt — into Claude. You can drag and drop them or use the attachment button. Alternatively, paste their contents directly into the chat.

3

Prompt #1 — Architecture Decision Record

With the files uploaded, send the following prompt to Claude:

Prompt #1 — Architecture Decision Record 
I've uploaded our current on-prem architecture for the Invoice Processing Service and the compliance requirements for migrating it to AWS.

Write an Architecture Decision Record (ADR) for this migration. Use this structure:

1. TITLE: ADR-001: Migration of Invoice Processing Service to AWS
2. STATUS: Proposed
3. CONTEXT: Why are we making this decision? (reference the ABBYY license deadline, current pain points, and compliance gaps)
4. DECISION: What architecture are we proposing? Include:
   - Compute: ECS Fargate (containerised) vs EC2 vs EKS — pick one and justify
   - Database: RDS PostgreSQL with Multi-AZ
   - File Storage: S3 with lifecycle policies
   - OCR: AWS Textract (replacing ABBYY) — compare capabilities and cost
   - Message Queue: SQS (replacing RabbitMQ)
   - Monitoring: CloudWatch + X-Ray (replacing Nagios)
5. ALTERNATIVES CONSIDERED: For each major component, list what else you considered and why you rejected it
6. CONSEQUENCES: What changes for the team? What are the risks?
7. MIGRATION APPROACH: Phased or big-bang? Recommend a phased approach with 3 phases.

Keep it concise but thorough. This goes to the Cloud Architecture Board.
4

Prompt #2 — Terraform Module + Security Review

In the same conversation, send this follow-up prompt:

Prompt #2 — Terraform + Security 
Now generate two deliverables:

DELIVERABLE 1: Terraform Module Skeleton
Write a Terraform module for the core infrastructure. Include:
- VPC with public/private subnets across 2 AZs
- ECS Fargate cluster with task definition (placeholder for container image)
- RDS PostgreSQL instance (Multi-AZ, encrypted, private subnet)
- S3 bucket for invoice files (encrypted with KMS CMK, versioning, lifecycle policy for 7-year retention, block public access)
- SQS queue for async processing
- Security groups with least-privilege rules
- KMS key for encryption

Use Terraform best practices: variables for configurable values, outputs for important resource IDs, tags for cost allocation. Include comments explaining security-relevant configurations.

DELIVERABLE 2: Security Compliance Review
Map the proposed architecture against each section of the compliance requirements document. For each of the 10 sections, provide:
- REQUIREMENT: One-line summary
- STATUS: Compliant / Partially Compliant / Gap
- EVIDENCE: How the Terraform module addresses it (or what's missing)
- ACTION NEEDED: For any gaps, what still needs to be done

Format as a table. Flag any P0 gaps that would block the Architecture Board approval.
5

Prompt #3 — Cost Projection

Still in the same conversation, send the final prompt:

Prompt #3 — Cost Projection 
Create a cost projection comparing current on-prem costs vs the proposed AWS architecture.

CURRENT ON-PREM COSTS (annual):
- 2x Dell PowerEdge servers: amortised ~$8,000/year (3-year refresh cycle, $12K each)
- 1x Database server: amortised ~$5,000/year
- SAN storage (NetApp): ~$18,000/year (maintenance + capacity)
- ABBYY OCR license: $45,000/year
- F5 load balancer: ~$6,000/year (maintenance share)
- RabbitMQ / Nagios: $0 (open source, but ~0.2 FTE to maintain = ~$30,000 in engineering time)
- Data center allocation: ~$15,000/year (power, cooling, rack space share)
- Total estimated: ~$127,000/year

AWS PROJECTED COSTS:
Estimate monthly costs for each AWS service based on the traffic patterns in the architecture doc (12K submissions/day average, 3x peaks, 890GB database, 4.2TB file storage). Use realistic us-east-1 pricing.

Include:
1. A side-by-side comparison table: Component | On-Prem Annual | AWS Annual | Difference
2. Total Cost of Ownership for Year 1 (include migration costs: engineering time, parallel running, training)
3. Total Cost of Ownership for Year 2+ (steady state)
4. Break-even analysis: When does the migration pay for itself?
5. Risk factors that could increase AWS costs (data transfer, peak scaling, storage growth)

End with a one-paragraph executive summary: "The migration will cost $X in Year 1 and save $Y annually starting Year 2, paying for itself by [date]. The primary cost driver is [X]."

Format for presentation to the CAB — clean tables, clear numbers.
6

Review & Iterate

Review all four deliverables. Check the ADR for clear justification of each technology choice. Verify the Terraform follows security best practices. Confirm the security review identifies real gaps (not just blanket compliance). Validate the cost estimates against your own knowledge of AWS pricing. Ask Claude to refine anything that needs adjustment. Compare your results with your lab partner — did Claude produce similar recommendations? Where did they differ?

Solution Walkthrough — Admin Only

Complete the lab first! The facilitator will review the solution with you.

Solution

What Good Looks Like

Use this evaluation guidance to assess the quality of each deliverable. The specifics below reflect what a strong response should include based on the sample data.

Solution Walkthrough

ADR Evaluation

The Architecture Decision Record should clearly recommend the following technology choices with justification:

  • ECS Fargate — recommended over EC2 (too much operational overhead for a small team) and EKS (too complex for team size; Kubernetes operational burden not justified). Fargate eliminates server management entirely.
  • RDS PostgreSQL Multi-AZ — managed database with automatic failover, encrypted at rest and in transit
  • S3 with lifecycle policies — 7-year retention for compliance, then transition to Glacier. Versioning enabled. Block all public access.
  • AWS Textract — replacing ABBYY. Pay-per-page pricing (no license lock-in), native AWS integration, comparable accuracy for structured invoices
  • SQS — replacing RabbitMQ. Fully managed, no operational overhead, native integration with ECS and Lambda
  • CloudWatch + X-Ray — replacing Nagios. Native AWS monitoring with distributed tracing

The migration approach should recommend 3 phases:

  • Phase 1: VPC, compute (ECS), database migration (RDS)
  • Phase 2: S3 migration (file storage), OCR switch (ABBYY to Textract)
  • Phase 3: Cutover, DR setup, decommission on-prem infrastructure

Terraform Evaluation

The Terraform module should demonstrate security best practices:

  • VPC — proper CIDR block, private subnets for RDS and ECS tasks, public subnets for ALB only
  • RDS — must include storage_encrypted = true, publicly_accessible = false, multi_az = true
  • S3 — must include block_public_access (all four settings), versioning enabled, server_side_encryption_configuration with KMS CMK
  • Security Groups — should demonstrate least-privilege: ALB allows 443 inbound, ECS only accepts traffic from ALB SG, RDS only accepts traffic from ECS SG
  • Variables — configurable values for environment, CIDR ranges, instance sizes, retention periods
  • Tags — cost allocation tags on all resources (project, environment, team)

Security Review Evaluation

Most sections should show Compliant or Partially Compliant. Key gaps that should be identified:

  • Section 2 — mTLS between services: Gap — mTLS between ECS services not configured in the base Terraform module. Needs App Mesh or service mesh implementation.
  • Section 6 — Macie for PII discovery: Gap — Amazon Macie not included for automated PII detection in S3 invoice files. Needs to be added.
  • Section 7 — DR runbook quarterly testing: Gap — DR infrastructure is defined but quarterly testing process and runbook are not automated. Needs operational procedure.
  • Section 8 — Container image scanning pipeline: Gap — ECR image scanning is available but CI/CD pipeline integration for blocking vulnerable images is not defined in the module.

These should be flagged as action items, not blockers for the Architecture Board approval.

Cost Projection Evaluation

AWS annual costs should be roughly $85K–$110K, broken down approximately as:

  • ECS Fargate: ~$18K/year (based on task sizing for 12K submissions/day with 3x peak capacity)
  • RDS PostgreSQL: ~$20K/year (Multi-AZ db.r6g.xlarge for 890GB database)
  • S3 Storage: ~$6K/year (4.2TB with lifecycle policies transitioning to Glacier)
  • AWS Textract: ~$8K/year (pay-per-page for 12K invoices/day)
  • Networking / NAT Gateway: ~$8K/year
  • CloudWatch / X-Ray: ~$3K/year
  • Miscellaneous (SQS, KMS, data transfer): ~$10K/year

Year 1 should be higher due to migration costs (~$50K in engineering time for parallel running, containerization, data migration, and training). Break-even should be around month 14–18 after migration start.

Evaluation Checklist

  • Does the ADR clearly justify each technology choice?
  • Does the Terraform follow security best practices (encryption, private subnets, least-privilege SGs)?
  • Does the security review identify real gaps (not just say "everything is compliant")?
  • Are cost estimates reasonable and based on actual AWS pricing?
  • Could you present these four documents at a real Architecture Board meeting?

Wow Realization

You just produced an ADR, a Terraform module, a compliance review, and a cost projection — four documents that typically take 2–3 weeks of meetings and async drafting. They're not final (they shouldn't be), but they're 80% there. You're walking into the Architecture Board with draft deliverables instead of blank slides.

Takeaway

Key Takeaway

Before AI

  • Migration planning takes 3–4 weeks
  • Architecture, security, IAC, and cost are reviewed in separate silos
  • Documents are inconsistent across deliverables
  • By the time you have all four, the first one is already outdated
  • Meetings start with blank whiteboards

After AI

  • All four deliverables generated together in one session
  • Consistent, cross-referenced, and ready for review
  • The Architecture Board gets a complete package, not a piecemeal drip-feed
  • Terraform references the ADR decisions, security review references the Terraform
  • Meetings start with draft deliverables to critique

AI doesn't make the migration decision for you — it eliminates the weeks of document preparation so you can spend your time on the decisions that matter: what to build, how to build it, and when to cut over.
